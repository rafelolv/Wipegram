# Releases

1. Inspect working-tree changes and existing local/remote tags and releases. Choose an unused three-part version. Preserve unrelated changes and published history. A published version or tag must never be reused or moved.
2. Align package and lockfile with `npm version <version> --no-git-tag-version`. Run `npm ci` and `npm run check`. Review the regenerated userscript and both packages. Run relevant browser checks from [MAINTENANCE.md](MAINTENANCE.md), or record why they were unavailable.
3. Move applicable `Unreleased` changes into a dated `CHANGELOG.md` section. Create `docs/releases/v<version>.md` from [RELEASE-TEMPLATE.md](RELEASE-TEMPLATE.md), replacing all placeholders. Write English bullets for changes, actual validation and limitations. Update versioned download examples in README and extension docs when applicable. Do not infer live deletion or Firefox compatibility from Chromium fixtures.
4. Run `npm run check:release -- v<version>` to validate the version, lockfile, changelog and notes and produce `dist/release/SHA256SUMS` for the userscript, both ZIPs and license. Run this after the build; it does not replace artifact validation. Review all prepared files before committing them under the repository-local maintainer identity.
5. When publication is requested, push the prepared `main` commit, create an annotated `v<version>` tag at that exact commit, and push the tag. The Release workflow checks that commit and publishes the userscript, versioned Chromium/Firefox ZIPs, `LICENSE` and `SHA256SUMS`. Ordinary builds, pushes to main and pull requests do not publish releases.
6. Inspect the workflow and GitHub release. Verify tag/commit, notes, exact asset names, download every asset into a temporary directory and run `sha256sum -c SHA256SUMS` there. Compare the downloaded manifest with `dist/release/SHA256SUMS` from the validated tagged build. A pushed tag alone is not a verified release. If publication fails, inspect remote state before retrying; never replace an existing release or upload over existing assets.
7. Report release URL, actual validation and outstanding limitations. These ZIPs remain unsigned local packages. Store submission, signing and review are separate and require specific authorization for Wipegram.

The [main install link](https://raw.githubusercontent.com/rafelolv/Wipegram/main/wipegram.user.js) follows ongoing development; release attachments are fixed snapshots. No version bump, tag, push, GitHub publication or store submission is implied by preparing these instructions.
